# Phase 3 face recognition: model and license review

**Review date:** 2026-10-20  
**Decision:** Recognition model not approved; do not download, bundle, or deploy pretrained recognition weights until the open license/data-provenance question is resolved. No model was downloaded and no recognition code or endpoint was added.

## Repository audit

- Backend is Node.js/Express, Mongoose/MongoDB, JWT authentication, and requires Node `>=20.9.0` (workspace runtime: Node 24.20.0).
- Employees carry a `branchId`; `requireOperationsAccount` reloads the account and verifies the matching active branch. Employee APIs query using that server-derived branch.
- Reference-photo bytes are normalized to WebP by Sharp with EXIF removed. The Cloudinary adapter retrieves a photo only by its server-stored authenticated asset ID through a short-lived private download request. Recognition must call this existing path only after resolving the active branch and branch-filtered employees.
- The current employee schema permits one optional photo per employee. Employees without a photo can be filtered out. There is no embedding schema/cache to invalidate.
- The current app does not expose an uploaded group image to the backend. The browser keeps image data in IndexedDB and the session API stores annotations and image metadata, not image bytes. A future recognition API would need an authenticated multipart upload and must avoid permanent storage.
- Sharp enforces 5 MiB by default (configurable up to 10 MiB), 25 million decoded pixels, and 10,000-pixel dimensions for reference uploads. The group image needs its own bounded validator and route-specific rate limit; existing `rateLimit.js` only serves the auth routes and is an in-memory per-process map.
- No OpenCV, ONNX Runtime, Python, or face model dependency is installed. No Render service manifest, Dockerfile, or worker deployment config is present. Current Node service is not prepared to run native OpenCV or a Python model worker.
- Fabric.js annotations and PNG export live in `ImageCanvas.jsx`, `AnnotationTag.jsx`, `PresenceEditor.jsx`, and `exportImage.js`. They were inspected; Phase 3 should return results only and should not modify these files.

## License and source evidence

- [OpenCV Zoo SFace model README](https://github.com/opencv/opencv_zoo/blob/main/models/face_recognition_sface/README.md) identifies SFace, its MobileFaceNet-based model files, and says all files in that directory are Apache-2.0.
- [OpenCV Zoo SFace model license](https://github.com/opencv/opencv_zoo/blob/main/models/face_recognition_sface/LICENSE) contains the Apache-2.0 terms. Preserve the license and notices if the artifact is later approved and distributed.
- [OpenCV Zoo issue #313](https://github.com/opencv/opencv_zoo/issues/313) requests authoritative answers on the exact SFace checkpoint's dataset, upstream authorization, and commercial use; it remains unresolved in this review.
- [OpenCV Zoo YuNet README](https://github.com/opencv/opencv_zoo/blob/main/models/face_detection_yunet/README.md) identifies the `2023mar` model, states all directory files are MIT, and links the training source.
- [YuNet training source](https://github.com/ShiqiYu/libfacedetection.train) identifies WIDER Face as the training dataset and uses BSD-3-Clause for its training code. Its code license alone does not grant rights to the training images or establish the pretrained checkpoint's downstream commercial terms.
- [dlib model author's training-data and model notes](https://github.com/davisking/dlib-models) explicitly state that the face recognition model's training data excludes commercial use.
- [InsightFace official model licensing note](https://github.com/deepinsight/insightface/tree/master/python-package) states supplied pretrained model packs are under separate terms and intended for non-commercial research by default.
- [OpenCV contrib face-recognition module](https://github.com/opencv/opencv_contrib/tree/4.x/modules/face) includes Eigenfaces, Fisherfaces, and LBPH algorithms. [OpenCV's Apache-2.0 license](https://github.com/opencv/opencv/blob/4.x/LICENSE) applies to the code, not employee photo rights or privacy obligations.

This is a technical source review, not legal advice. The organization should obtain a written model/data permission or an internal legal review before operational biometric use.

## Implementation gate and suggested next step

Do not add a dummy recognition route, use a fallback identity, or treat mocked scores as working recognition. First obtain written confirmation from OpenCV/model authors that identifies the training data for the exact SFace checkpoint and clears the intended organizational use, or provide another exact model artifact with a license and dataset provenance that explicitly permit this use. Then pin its source revision and SHA-256 and document notices before implementation.

If no suitable pretrained artifact can be cleared, one clear-weight path is an evaluated classical OpenCV LBPH recognizer trained from organizationally authorized enrollment photos, subject to its significant accuracy limitations and an additional cleared face detector. The higher-accuracy path is to commission or train a model using training data with documented rights for this use. That option has substantial model-training, evaluation, and compute work and cannot be replaced by simply fine-tuning on the current single reference photo per employee. A self-hosted detector/recognizer also requires Render CPU/memory benchmarking; there are no measured resource requirements for this repository today.

## Privacy and intended matching behavior

Any eventual endpoint must keep reference photos and embeddings branch-scoped and server-side, accept no client-selected employee or storage identifiers, avoid retaining group photos or recognition results, rate-limit work, and return `unknown`/`ambiguous` rather than a forced match. Similarity scores must be labeled as model scores, not probabilities. One reference photo per employee is a weak enrollment basis for changes in pose, lighting, expression, distance, and partial occlusion; evaluate additional enrollment images only after consent/notice and a documented retention policy. Recognition cannot establish physical presence or infer attendance/attire decisions.
